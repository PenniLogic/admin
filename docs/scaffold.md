# Admin console scaffold

Plan item `T-SCA-ADM-01` — [PenniLogic/admin#1](https://github.com/PenniLogic/admin/issues/1).

The administrative console is a separate service with a separate authorization domain
([ADR-014](https://github.com/PenniLogic/docs/blob/main/adr/ADR-014.md); security architecture §2.3).
This scaffold makes that separation structural from the first commit:

- **Deny-only boundary.** No administrative identity provider is configured, so `proxy.ts` refuses
  every request before routing and the catch-all route refuses anything that reaches routing.
- **Import boundary.** Source may import only Node.js builtins, this repository's own files and
  packages declared in `package.json` and resolved from the public npm registry. Customer web code,
  shared client bundles and every PenniLogic package are refused (see below).
- **Contract statement.** The admin console consumes the administrative API only, through the
  administrative contract that the `contracts` repository will publish separately. It never
  consumes the customer API and never shares route groups, middleware, session code or runtime
  configuration with the customer web application.

Administrative features, authentication and policy belong to E13 and are out of scope here.

## Toolchain

| Component | Locked version | Where |
| --- | --- | --- |
| Node.js | 24.14.0 (24.x LTS) | `.nvmrc`, `engines.node`, `.npmrc` `engine-strict=true` |
| npm | 11.9.0 (11.x) | `packageManager`, `engines.npm` |
| Next.js / React | 16.3.7 / 19.2.8 | `package.json`, exact versions only |
| TypeScript / ESLint / Vitest | 5.9.3 / 10.11.0 / 5.0.2 | `package.json` |

Dependencies are exact registry releases; `package-lock.json` (lockfile version 3) is the only
provenance and every entry must resolve to the public registry with a sha512 hash. Build and test
telemetry is disabled for every Next.js invocation by `tools/next-cli.mjs`; the scaffold ships build
and test metrics only.

## Commands

```text
npm ci
npm run lint            # ESLint 10 flat config: eslint recommended, typescript-eslint strict + stylistic (type-aware), @next/eslint-plugin-next core-web-vitals, no-restricted-imports mirror
npm run typecheck       # next typegen, then tsc --noEmit with strict options (also checks the @ts-check tools)
npm run check:imports   # tools/import-boundary/check.mjs: manifest, lockfile and every source file
npm test                # Vitest unit project with 100 % line/branch/function/statement coverage thresholds
npm run build           # next build (Turbopack) — production output in .next/
npm run smoke           # Vitest smoke project against `next start` of the production build
npm run verify          # all of the above, in this order
```

`next-env.d.ts` is regenerated by `next typegen` and `next build` and is not committed; its ignore
pattern is requested through the generated setup owned by `PenniLogic/infra/governance`, because
`.gitignore` is a generated file.

## Denial response

Every method on every path receives `403` with `content-type: text/html; charset=utf-8`,
`cache-control: no-store`, `content-security-policy: default-src 'none'; frame-ancestors 'none';
base-uri 'none'; form-action 'none'`, `x-content-type-options: nosniff`, `x-frame-options: DENY`,
`referrer-policy: no-referrer` and `admin-denial-reason: no-administrative-identity-provider`.
`HEAD` carries the same headers and no body. No cookie header is ever set, no redirect is issued and
no `x-powered-by` header is emitted.

The page is a complete `lang="en"` document with a `<title>`, a `<main>` landmark, one `<h1>`, a
viewport meta tag and a `noindex, nofollow` robots meta tag. It loads no script, style, image, font,
link or external resource, so it renders identically under the strict policy above and with assistive
technology. It names no identity provider, hostname or customer surface.

Known framework behaviour: Next.js collapses repeated leading slashes (`//path`) to the same-origin
path with a `308` before any proxy runs, so a path can never be read as a protocol-relative host; the
collapsed path is then denied. The smoke test pins this.

## Import boundary

`tools/import-boundary/policy.mjs` defines the rules; `scan.mjs` applies them to every `.ts`, `.tsx`,
`.mts`, `.cts`, `.js`, `.mjs`, `.cjs` and `.jsx` file outside `node_modules`, `.next`, `.git` and
`coverage`, to `package.json` and to `package-lock.json`:

| Rule | Refuses |
| --- | --- |
| `customer-web-or-shared-client` | Any specifier naming `customer-web`, `customer-client`, `customer-app`, `shared-client`, `web-client` or `client-bundle` |
| `organization-package-not-allowed` | Every `@pennilogic/*` and `pennilogic-*` package not listed in `ALLOWED_ORGANIZATION_PACKAGES` (empty until the administrative contract exists) |
| `escapes-repository` | Relative or `@/` imports that resolve outside this repository or into `node_modules` |
| `absolute-or-remote-specifier` | Absolute paths, drive letters, `file:`, `http(s):`, `data:` and direct `node_modules/` specifiers |
| `non-literal-dynamic-specifier` | Dynamic `import()` or `require()` whose argument is a variable, expression or template with placeholders |
| `undeclared-dependency` | Bare specifiers whose package is not declared in `package.json` |
| `non-registry-or-inexact-dependency` | `file:`, `link:`, `workspace:`, git, URL, `npm:` alias or range versions |
| `workspace-or-bundled-dependency` | `workspaces`, `bundleDependencies`, `bundledDependencies` or `overrides` in the manifest |
| `lockfile-provenance` | Lockfile entries that are linked, outside `node_modules`, not from the public registry, without a sha512 hash, refused packages, or a root entry that disagrees with the manifest |

Static, type-only, side-effect, re-export, dynamic `import()` and `require()` specifiers are all
extracted, and any dynamic argument that is not a plain string literal is refused outright. The
name-based rules are mirrored into ESLint `no-restricted-imports`, so a planted
customer import fails `npm run lint`, `npm run check:imports` and `npm test`. The rules are
structural on purpose: this repository records neither the customer session cookie name nor any
customer hostname.

## Acceptance mapping

| Acceptance criterion | Evidence |
| --- | --- |
| Clean clone builds, lints and tests with the documented commands | `npm ci && npm run verify` (recorded in the pull request) |
| An attempted import of customer web code fails the pipeline | `tests/unit/import-boundary.test.ts` — planted fixtures, end-to-end planted repository, command-line exit 1, ESLint mirror |
| The default route returns a denial | `tests/unit/proxy.test.ts`, `tests/unit/route.test.ts`, `tests/smoke/server.test.ts` |
| No customer session cookie name or domain appears anywhere | `tests/unit/no-customer-artifacts.test.ts` — no cookie handling, no hostname literals outside tooling hosts, registry-only lockfile, no customer-like fixtures |
| Admin API only, never the customer API | This document and `ALLOWED_ORGANIZATION_PACKAGES` in `policy.mjs` |
| Default deny before any authentication | `tests/unit/authorize.test.ts` — the decision type has no allowed member |

## Continuous integration

Until the generated setup in `PenniLogic/infra/governance` adds the Node.js toolchain and the
commands above, the native `CI` job runs `python scripts/check_repository.py` only. The Node.js
results are local evidence recorded in the pull request; a foundation check is not a build, test,
accessibility or load acceptance claim.

## Rollout and rollback

Merged to `main`; nothing is deployed. Rollback is a revert of the merge commit with no user impact.
