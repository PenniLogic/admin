# Admin console scaffold

Plan item `T-SCA-ADM-01` — [PenniLogic/admin#1](https://github.com/PenniLogic/admin/issues/1).

The administrative console is a separate service with a separate authorization domain
([ADR-014](https://github.com/PenniLogic/docs/blob/main/adr/ADR-014.md); security architecture §2.3).
This scaffold makes that separation structural from the first commit:

- **Deny-only boundary.** No administrative identity provider is configured, so `proxy.ts` refuses
  every request the framework forwards, before routing; the catch-all route is a backstop behind it.
- **Import boundary.** Runtime source (`proxy.ts`, `app/**`, `src/**`, `next.config.ts`) imports only
  `next`, `react`, `react-dom` and repository files through `@/`, and references no process, global,
  module-system, network or timer identifier at all. Every other source file may import only Node.js
  builtins, repository files and packages declared in `package.json` and resolved from the public
  npm registry. Customer web code, shared client bundles and every PenniLogic package are refused;
  the enumerated loader names, computed member access on the module-system bindings, non-literal
  dynamic specifiers, links and dot-segment subpaths are refused; and the compiler, bundler and
  test-runner resolution surfaces are pinned. See "Import boundary" for exactly what is enforced.
- **Contract statement.** The admin console consumes the administrative API only, through the
  administrative contract that the `contracts` repository will publish separately. It never
  consumes the customer API and never shares route groups, middleware, session code or runtime
  configuration with the customer web application.

Administrative features, authentication and policy belong to E13 and are out of scope here.

## Commands

```text
npm ci
npm run lint            # ESLint 10 flat config: eslint recommended, typescript-eslint strict + stylistic (type-aware), @next/eslint-plugin-next core-web-vitals, import-boundary mirror rules
npm run typecheck       # next typegen, then tsc --noEmit with strict options (also checks the @ts-check tools)
npm run check:imports   # tools/import-boundary/check.mjs: manifest, lockfile, configuration and every source file
npm test                # Vitest unit project; 100 % line/branch/function/statement thresholds over app/**, src/**, proxy.ts, policy.mjs and scan.mjs
npm run build           # next build (Turbopack) — production output in .next/
npm run smoke           # Vitest smoke project against `next start` of the production build (requires the build)
npm run verify          # all of the above, in this order
```

The coverage thresholds cover the runtime source and the scanner library. `tools/import-boundary/check.mjs`,
`tools/next-cli.mjs` and `tests/support/**` are exercised by the tests (the command line through a
child process) but are outside the threshold scope.

`next-env.d.ts` is regenerated by `next typegen` and `next build` and is not committed; the generated
`.gitignore` (owned by `PenniLogic/infra/governance`) ignores it together with `*.tsbuildinfo`.

ESLint lints `.ts`/`.tsx`/`.mts`/`.cts` with type information from the project service and
`.js`/`.jsx`/`.mjs`/`.cjs` without it; the scanner parses all eight extensions regardless.

| `src/boundary/denial.ts` | Denial status, headers and the neutral self-contained denial page |

| `tools/import-boundary/scan.mjs` | Scanner library: TypeScript-AST import extraction, manifest, lockfile, tsconfig, next.config, source discovery |

| `tests/fixtures/import-boundary/` | Planted forbidden imports as `.txt` (never compiled) plus two clean controls |

## Denial response

Every request the framework forwards — every method (`GET`, `HEAD`, `POST`, `PUT`, `PATCH`, `DELETE`,
`OPTIONS`, `PROPFIND`, `PURGE`, `QUERY`, ...) on every path, including existing built assets and
the image optimizer — receives `403` with exactly these headers: `content-type: text/html; charset=utf-8`,
`cache-control: no-store`, `content-security-policy: default-src 'none'; frame-ancestors 'none';
base-uri 'none'; form-action 'none'`, `x-content-type-options: nosniff`, `x-frame-options: DENY`,
`referrer-policy: no-referrer`. `HEAD` carries the same headers and no body. No cookie header is
ever set, no redirect is issued, no `x-powered-by`, `server`, `allow`, `www-authenticate`,
`access-control-*` or `x-middleware-*` header is emitted, and no header or body text describes the
service, its configuration or the decision reason (which stays in `authorize.ts` and the tests).

The page is a complete `lang="en"` document with a `<title>`, a `<main>` landmark, one `<h1>Access
denied</h1>`, one neutral sentence ("This service does not accept requests."), a viewport meta tag
and a `noindex, nofollow` robots meta tag. It loads no script, style, image, font, link or external
resource and offers no recovery or sign-in hint, so it renders identically under the strict policy
above and with assistive technology.

### Requests answered by the framework before the boundary

Next.js 16.3.7 answers four request classes itself, before `proxy.ts` runs. None is a denial, none
sets a cookie or serves content, and none can be changed from application code. They are pinned in
`tests/smoke/server.test.ts` so a framework change is noticed:

| Request | Framework behaviour |
| --- | --- |
| Repeated leading slashes (`//path`) | `308` to the same-origin collapsed path (`/path`), which is then denied |
| `TRACE` (any path) | `500 Internal Server Error`, `text/plain`, none of the denial headers; the framework logs a `TypeError` stack trace per request because the WHATWG `Request` constructor refuses the method. `TRACK` is a `400` from Node's parser and `CONNECT` receives no response |
| Asterisk-form target (`OPTIONS *`, any method) | `500 Internal Server Error`; the framework logs `TypeError: Invalid URL` |
| Absolute-form target (`GET https://other.example/x HTTP/1.1`) | `308` with `Location:` set to the supplied absolute URL, no `Cache-Control` or CSP. Browsers never send this form to an origin server, so no browser can be redirected by it, but it is not same-origin |
| `Upgrade: websocket` | No response at all; the socket is left open for a custom WebSocket server that does not exist |

**Deployment requirement.** The edge in front of this service (reverse proxy, load balancer or WAF)
must reject `TRACE`, `TRACK` and `CONNECT`, asterisk-form and absolute-form request targets, and
`Upgrade` requests before they reach Next.js. Until an edge exists, nothing is deployed.

## Import boundary

`tools/import-boundary/policy.mjs` defines the rules; `scan.mjs` applies them to every `.ts`, `.tsx`,
`.mts`, `.cts`, `.js`, `.mjs`, `.cjs` and `.jsx` file outside `node_modules`, `.next`, `.git` and
`coverage`, to `package.json`, `package-lock.json`, `tsconfig.json` and the Next.js configuration.
Source is parsed with the TypeScript compiler API, so every form the compiler understands is
checked: `import`/`export ... from`, `import type`, `import x = require()`, `import("x")` in type
position, dynamic `import()`, `require()`, and `/// <reference>` directives.

The guarantee is enumerated, not open-ended. What the scanner enforces:

### Runtime source (`proxy.ts`, `app/**`, `src/**`, `next.config.ts`) — positive allowlist

| Rule | Enforces |
| --- | --- |
| `runtime-import-not-allowed` | Only `next`, `react`, `react-dom` (any subpath) and `@/` repository files may be imported. Relative imports, Node.js builtins and every other package are refused |
| `runtime-reference-not-allowed` | No reference, as an identifier or a string-literal member key, to `process`, `globalThis`, `global`, `window`, `self`, `module`, `exports`, `require`, `eval`, `Function`, `Reflect`, `Proxy`, `WebAssembly`, `fetch`, `XMLHttpRequest`, `WebSocket`, `EventSource`, `Worker`, `SharedWorker`, `importScripts`, `setTimeout`, `setInterval`, `setImmediate`, `queueMicrotask`, `structuredClone`, `AsyncFunction`, `GeneratorFunction`, `AsyncGeneratorFunction`, or `import.meta` / `new.target` |
| `computed-member-access` | No computed member access at all except numeric or string-literal keys (`a[0]`, `a["b"]`) |

The deny-only runtime needs none of these, so this is structural: a loader assembled from computed
members or fetched through `process` cannot be written in runtime source without tripping a rule.

### Every source file

| Rule | Refuses |
| --- | --- |
| `customer-web-or-shared-client` | Any specifier naming `customer-web`, `customer-client`, `customer-app`, `shared-client`, `web-client` or `client-bundle` |
| `organization-package-not-allowed` | Every `@pennilogic/*` and `pennilogic-*` package not listed in `ALLOWED_ORGANIZATION_PACKAGES` (empty until the administrative contract exists) |
| `escapes-repository` | Relative, alias (`@/`) or triple-slash targets whose real path (links resolved) is outside this repository or inside `node_modules`; every symbolic link or junction found inside the tree (refused rather than followed); bare package subpaths containing a `.` or `..` segment; any specifier containing a backslash or percent-encoding |
| `absolute-or-remote-specifier` | Absolute paths, drive letters, `file:`, `http(s):`, `data:`, direct `node_modules/` and package subpath (`#name`) specifiers |
| `non-literal-dynamic-specifier` | Any dynamic `import()` or `require()` whose argument list is not exactly one plain string literal: variables, concatenation, method calls, template placeholders, a second (attributes) argument |
| `indirect-module-loader` | Any reference (identifier, property name or string-literal element key) to `createRequire`, `eval`, `Function`, `constructor`, `getBuiltinModule`, `binding`, `dlopen`, `mainModule`, `_load`, `runInThisContext`, `runInNewContext`, `runInContext`, `compileFunction`; `new Function`; `require.resolve`; `import.meta.resolve`; `require` in any position other than the callee of a direct call (`module.require`, `require.main.require`, `const r = require`); importing `module`, `vm`, `worker_threads`, `child_process` or `process` outside the four files listed in `LOADER_BUILTIN_ALLOWANCES` (the scanner itself for `builtinModules`, the Next CLI wrapper and two tests for `child_process`) |
| `computed-member-access` | Element access with a non-literal key on `process`, `globalThis`, `module`, `require`, `window`, `self`, `import.meta`, or any binding imported from a loader builtin in that file |
| `undeclared-dependency` | Bare specifiers whose package is not declared in `package.json`; `node:` specifiers that do not name a real builtin |
| `non-registry-or-inexact-dependency` | `file:`, `link:`, `workspace:`, git, URL, `npm:` alias or range versions |
| `workspace-or-bundled-dependency` | `workspaces`, `bundleDependencies`, `bundledDependencies`, `overrides` or `imports` in the manifest |
| `lockfile-provenance` | Lockfile entries that are linked, outside `node_modules`, not from the public registry, without a sha512 hash, refused packages, or a root entry that disagrees with the manifest |
| `resolution-surface` | `tsconfig.json` missing, unparsable, with `compilerOptions.paths` other than exactly `{"@/*": ["./*"]}`, or with `baseUrl`, `rootDirs`, `rootDir`, `typeRoots`, `types`, `extends`, `references`, `files` or an `include` outside the repository; `next.config.ts` missing, containing any key outside `reactStrictMode`, `poweredByHeader`, `skipTrailingSlashRedirect`, `skipProxyUrlNormalize`, or any call, spread or computed key; any `next.config.{js,mjs,cjs,mts,cts,json}` sibling (Next.js would load it before `next.config.ts`) |

The Vitest alias (`/^@\//` → repository root, nothing else) is pinned by a unit test that imports the
configuration. A comment inside a call or a syntactically invalid specifier does not hide an import:
whatever the parser kept is checked as written.

Known strictness: a `Function` type annotation, an object property named `eval` or `constructor`,
and any `.constructor` access are reported as `indirect-module-loader`; write the type as a
signature and rename the property. Outside runtime source, computed access on ordinary objects
(`manifest[field]`) is acceptable.

What the scanner does **not** cover: behaviour of installed packages themselves (provenance is the
control there), and code loading that starts outside this repository (the deployment edge and the
runtime allowlist are the controls there).

The static-import name rules, the loader names and the runtime allowlist are mirrored into ESLint
(`no-restricted-imports` patterns and paths, `no-restricted-globals` for runtime source, `no-eval`,
`no-implied-eval`, `no-new-func`, `no-restricted-properties`, `no-restricted-syntax`), so a planted
static customer import, loader or runtime reference fails `npm run lint` as well as
`npm run check:imports` and `npm test`. The mirror covers what ESLint can see syntactically; the
scanner is authoritative for dynamic forms, escapes, configuration and provenance.

The rules are structural on purpose: this repository records neither the customer session cookie
name nor any customer hostname. The hostname tripwire in `tests/unit/no-customer-artifacts.test.ts`
is a heuristic with a finite top-level-domain list; the guarantees are the import boundary and the
absence of any cookie handling.

## Acceptance mapping

| Acceptance criterion | Evidence |
| --- | --- |
| Clean clone builds, lints and tests with the documented commands | `npm ci && npm run verify` locally and in the native `CI` job (recorded in the pull request) |
| An attempted import of customer web code fails the pipeline | `tests/unit/import-boundary.test.ts` — planted fixtures for every form (static, type-only, `import =`, type-position `import()`, dynamic, concatenated, two-argument, commented, template, variable, `createRequire`, `getBuiltinModule` proxy, computed members, `eval`, `Function`, `.constructor`, `require.resolve`, `import.meta.resolve`, aliased and member `require`, `vm`/`worker_threads`/`child_process`, relative/alias/triple-slash/percent-encoded escapes, links, package dot-segment subpaths, subpath imports, absolute/remote, runtime builtin/package/global references), planted into a copy of the repository and into an existing runtime file, command-line exit 1, ESLint mirror, configuration surfaces and configuration siblings |
| The default route returns a denial | `tests/unit/proxy.test.ts`, `tests/unit/route.test.ts`, `tests/smoke/server.test.ts` |
| No customer session cookie name or domain appears anywhere | `tests/unit/no-customer-artifacts.test.ts` — no cookie handling, no hostname literals outside tooling hosts, registry-only lockfile, no customer-like fixtures, no links in the tree, no process/global/module/loader reference in runtime source, exactly one Next.js configuration file |
| Admin API only, never the customer API | This document and `ALLOWED_ORGANIZATION_PACKAGES` in `policy.mjs` |
| Default deny before any authentication | `tests/unit/authorize.test.ts` — the decision type has no allowed member |

## Continuous integration

The native `CI` job (generated by `PenniLogic/infra/governance`) provisions Node.js 24.14.0 from
`.nvmrc` on `ubuntu-24.04` with `NEXT_TELEMETRY_DISABLED=1` and runs, in order:
`python scripts/check_repository.py`, `npm ci --no-audit --no-fund`, `npm run lint`,
`npm run typecheck`, `npm run check:imports`, `npm test`, `npm run build`, `npm run smoke`. Local
reproduction is the same command list from a clean clone. A green run is build, lint and test
evidence for this scaffold; it is not an accessibility or load acceptance claim.

## Rollout and rollback

Merged to `main`; nothing is deployed. Rollback is a revert of the merge commit with no user impact.
